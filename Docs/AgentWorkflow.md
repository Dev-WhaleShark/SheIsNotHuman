# 감독 기반 에이전트 운영

지속 규칙은 [AGENTS.md](../AGENTS.md)에 있다. 필요한 배정·인계·검증 절차만 참고한다.

## 시작과 작업 계약

1. 메인은 요청 범위, 기존 변경, 완료 조건을 확인하고 사용할 런타임을 알린다.
2. 감독은 현재 설정의 관련 역할을 선택하고 독립 작업과 공유 인터페이스를 정한다.
3. 작업마다 ID, 목표, 소유 파일, 선행 작업, 완료 조건, 관찰 가능한 검사를 기록한다.
4. 담당자는 배정 파일만 편집한다. 범위 확대·공유 파일 변경은 감독에게 소유권 조정을 요청한다.
5. 구현 결과를 모은 뒤 쓰기를 동결하고 구현자가 아닌 담당자가 최종 통합본을 검증한다.
6. 실패는 재현 → 원인 한정 → 담당자 수정 → 실패 검사와 영향받는 회귀 검사 재실행으로 처리한다.
7. 같은 실패가 세 번 반복되면 전제를 재검토한다. 필요한 외부 조치가 명확할 때 장애를 보고한다.

공유 디렉터리는 병합 없이 검증하고 별도 작업 트리 결과만 통합한다.
`implementer_lite`는 파일과 완료 조건이 좁고 분명한 작업에만 배정한다. 설계 판단이나 범위가 커지면 멈추고 감독에게 올린다.

## 현재 설정과 예외 역할

- 기본 설정: [config.toml](../.codex/config.toml). 책임별 재사용 역할은 선택한 사용자 Codex 홈의 `agents/`에서 확인한다. 씬·기능 전용 역할은 만들지 않고 해당 맥락을 작업 계약·적용 AGENTS·스킬로 전달한다. 선택 조건·입력·출력은 [역할 안내](AgentRoles.md)를 확인한다.
- 일반 역할은 `supervisor`, `implementer`, `implementer_lite`, `verifier`, 읽기 전용 `explorer`이며 이 문서에 모델 값을 복제하지 않는다. 선택 전 현재 런타임의 역할 발견 여부를 확인한다.
- 역할 선택 기능이 없으면 해당 역할의 책임, 소유권, 완료 조건과 독립 수행에 필요한 정보를 생성 요청에 전달한다.
- native Codex에서 모델·추론 수준을 명시할 때는 전체 이력 복제 대신 독립 작업에 필요한 최소 이력을 전달한다. max 자문은 이력을 상속하지 않는다.
- 설정 변경 후에도 기존 세션의 실제 모델·도구·한도를 확인한다.
- 요청값이 지원되지 않으면 확인된 가장 가까운 낮은 지원값으로 대체하고 요청·실제값·이유를 기록한다. 지원되지 않는 토큰 상한 필드를 추가하지 않는다.

Astra high 감독·검증 경로와 max 자문 경로의 선택 조건·동시 한도는 AGENTS를 따른다. 메인의 모델은 이 규칙으로 바꾸지 않는다.
Sol 감독은 max 자문에 승격 근거와 최소 관련 사실·파일을 전달하고, 문제 한 건 또는 밀접한 묶음으로 범위를 제한한다.
자문 결과는 결정·해법, 근거, 필요한 인터페이스, Sol 구현 작업, 검증 기준으로 받는다. 자문자가 다른 작업자를 만들지 않는다.
파일 수정·최소 필수 코드는 해결에 꼭 필요하고 감독이 특정 파일을 명시적으로 배정한 경우에만 허용한다.
첫 자문 후 종료하고 새 증거·중대한 장애가 생긴 경우에만 이유를 기록해 재자문한다.
Astra 감독에서 max 자문으로 전환하려면 먼저 감독을 종료하고 Sol 감독에게 상태·소유권을 인계한다.

## 탐색과 구현 경로

낯선 코드의 진입점·실행 경로가 불분명하거나 서로 독립적인 읽기 질문이 여러 개일 때만 `explorer`를 사용한다.
진입점과 수정 파일이 이미 명확한 단순 작업은 탐색을 생략하고 구현 계약을 배정한다.
탐색 입력은 질문, 읽을 범위, 이미 확인한 사실과 필요한 근거로 좁힌다. 탐색자는 파일을 수정하거나 구현자를 만들지 않는다.
출력은 진입점, 관련 파일·심볼·위치, 확인 근거, 남은 불확실성, 다음 쓰기 후보 파일만 간결하게 전달한다.
독립 읽기 작업은 활성 한도 안에서 병렬로 배정하며 같은 질문을 중복 조사하지 않는다. 탐색 결과는 현재 코드 근거로 통합한다.
감독은 쓰기 후보를 파일별 단일 작성자와 의존 관계가 명확한 구현 계약으로 바꾼다. 결과 통합 후 작성자를 동결하고 독립 검증한다.

## 런타임 조율

Orca 세션은 설치된 orchestration 스킬의 실행 파일 선택 규칙과 버전별 지침을 따른다. 명령·옵션을 복제하거나 추측하지 않는다.
감독은 실제 연결·작업 컨텍스트를 확인해 Run과 배정을 관리한다. 터미널 권한상 필요할 때만 메인이 호출을 중계한다.
Orca Task/Dispatch가 실시간 상태의 기준이다. 작업자는 주입된 preamble에 따라 질문·heartbeat·완료 보고를 보낸다.
완료 이벤트와 작업자 재사용·정리는 현재 CLI 계약을 따른다.
Windows 샌드박스의 명령 검색 실패를 미설치로 단정하지 않는다. 환경 근거가 있으면 승인 절차로 같은 실행 파일을 재시도하고 임의로 바이너리를 바꾸지 않는다.
런타임 전환 전 진행 작업, 작성자, 완료 결과를 대조하고 중복 배정을 막는다. Codex 기본 하위 에이전트를 Orca 작업자로 표현하지 않는다.

## 기록과 인계

감독 한 명이 실행별 작업 기록을 관리한다. native 실행은 `tmp/agent-runs/<run-id>/tasks.md`에 기록하며 자동 삭제하지 않는다.
Orca 실행은 Task/Dispatch를 원본으로 삼고 파일 기록은 필요할 때 결과 내보내기에 사용한다.
범위·기존 변경·계약·상태·요청/실제 모델·추론·선택 근거·검증·남은 조치를 기록한다.
상태는 계획·실행·구현 완료·검증·검증 완료로 구분하고 실패 시 수정 후 재검증한다.
`blocked`에는 구체적인 원인, 시도한 대안과 필요한 외부 조치를 남긴다. 작업자의 완료 보고만으로 verified를 부여하지 않는다.

Editor 인계에는 활성 프로젝트·인스턴스, 대상 씬·프리팹의 dirty/저장 상태, Play·컴파일 상태, 출력 에셋·.meta, 다음 담당자를 적는다.
감독은 관련 작성자 모두의 동결을 확인하고 최신 통합 파일 상태를 인계한다. 자동 가져오기·도메인 재로드도 이 조율에 포함한다.
Editor 담당자는 가져오기·컴파일 완료 후 씬·검사를 진행한다. 수정이 필요하면 검증을 멈추고 작성자에게 돌려준 뒤 재동결한다.
Builder/Migration의 코드 소유권과 간접 저장·생성되는 씬·프리팹·데이터·폰트 및 .meta 소유권을 실행 전에 각각 확정한다.

## 프로젝트 훅

프로젝트의 [hooks.json](../.codex/hooks.json)과 [훅 안내](../.codex/hooks/README.md)는 Codex의 실제 SessionStart/PreToolUse/PostToolUse 규격을 따른다. 기존 Orca 전역 훅은 수명·메시지 전송용이며 프로젝트 가드와 함께 실행된다. 훅 신뢰 검토는 지원되는 `/hooks` 또는 런타임 검토 절차로 수행하고 신뢰 파일을 직접 승인 상태로 바꾸지 않는다.

시작 훅은 적용 AGENTS와 제한된 git 문맥을 제공하고 실행 전 훅은 명확히 식별한 위험 명령과 보호 파일 편집을 검사한다. 실행 후 C# 공백 정리는 감독이 파일 소유권과 작성자 동결을 확인한 짧은 임대를 발행한 경우에만 바뀐 파일을 대상으로 실행한다. 임대가 없으면 생략한다. 임대는 협업 약속이며 OS 샌드박스나 모든 동시 쓰기를 막는 잠금이 아니다.

훅 오류와 셸 실패는 제한된 진단과 다음 조치로 돌려준다. 자동으로 코드를 고치거나 새로운 권한을 얻지 않는다. 훅의 런타임 오류가 실행 전 차단을 보장하지 않을 수 있으므로 기존 권한과 소유권 절차를 함께 지킨다.

## 산출물에 따른 검증

| 변경 산출물 | 필요한 근거 |
| --- | --- |
| 문서·에이전트 설정 | 크기·참조·설정 파싱·역할 충돌 등 변경에 맞는 검사. 게임 동작 변경이 없으면 Unity 실행을 요구하지 않는다. |
| C# 런타임·Editor 코드 | 실제 Unity 컴파일과 관련 검사. 생성 csproj 빌드만으로 Unity 검증을 대체하지 않는다. |
| 화면·입력·씬 | 대상 씬의 실제 화면·상호작용과 Console 결과. 대상은 요청과 현재 파일에서 확인한다. |
| Builder/Migration 출력 | 생성·수정 에셋과 .meta 목록, GUID·직렬화 참조, 실제 출력 씬·프리팹의 동작. |

검사마다 명령·도구 동작, 검사한 revision 또는 변경 파일 스냅샷, 종료 상태, 로그·산출물 경로를 남긴다.
테스트의 발견·실행·통과·실패·건너뜀 수와 미실행 사유를 구분한다. 메뉴 규칙 검사와 발견·실행된 NUnit 테스트 수는 별도 기록한다.
발견 0개는 성공 근거가 아니다. 변경 위험에 맞는 재현 시나리오와 필요한 회귀 검사를 수행하고 남은 공백을 명시한다.
검증 중 또는 이후 관련 파일이 바뀌면 영향받는 검사를 다시 실행한다. 기존 실패와 새 실패, 통과·실패·차단·미실행을 구분한다.
메인의 한국어 최종 보고에는 변경 결과, 실제 검사와 결과, 해결한 문제, 남은 장애·미검증 동작을 담는다.
